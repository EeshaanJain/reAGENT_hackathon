Chemical Perturbation · design note

An agent-based pipeline for running a perturbation benchmark

Given a fixed dataset, a fixed metric suite, and a fixed list of models, how do you actually get every model to run — correctly, comparably, and reproducibly — when each one ships as a different research repo with a different interface? This note specifies that runner: which parts are LLM agents, which parts must be deterministic code, how paperclip and the GitHub repo supply the context the agent needs, and which existing tools to reuse rather than rebuild.

Scoped deliverable · design + implementation plan · 2026-08-15

In scope — this document

  • Running the benchmark, given a pre-specified dataset, metric suite, and model list
  • Extracting run-critical context from the paper (via paperclip) and the code repo
  • Per-model environment construction and adapter synthesis
  • Execution, evaluation, audit, and reporting of results

Out of scope — upstream/downstream owners

  • Choosing the dataset or building the splits
  • Designing the metric suite
  • Selecting which models to benchmark
  • Interpreting biology or writing the paper

Each is treated here only as an interface: §7 specifies the minimum each must emit for this runner to be optimal.

1The one design decision that matters

Everything else in this document follows from a single split of labor.

LLM agents do comprehension and code generation. The runner is deterministic code.

Reading a paper's Methods section to learn that a metric is computed on Δ-from-control rather than on absolute expression, or reading a repo to learn that a model wants adata.X log-normalized but adata.layers['counts'] raw — that is language understanding over unstructured, inconsistent, human-written artifacts. There is no library for it, and an agent is genuinely the right tool.

Deciding which of 7 models × 3 splits × 5 seeds to launch next, computing a Pearson correlation, and writing a row to a results table are none of those things. If an agent does them, your benchmark is unreproducible: rerunning it re-samples the agent's decisions. So the agent's output is never a result — it is always a reviewable artifact (a config file, an adapter module, a container recipe) that deterministic code then consumes.

Critical · the failure this prevents
The reference harness for this space, TianGzlab/scPerturbBench, gives each model its own metrics_script and run_benchmark.py writes no results itself — it shells out to a model script and a metrics script per model. That is exactly how a benchmark becomes silently non-comparable: two models' numbers can differ because their metric code differs, and nothing in the pipeline surfaces it. Metrics must be computed once, by the harness, on saved prediction artifacts. Model code produces predictions and nothing else.

3Context harvest: what the paper knows vs what the repo knows

This is the stage the request is really about, and the division below is the finding that makes it work.

I tested this against a real benchmark paper. The result is clean and it generalizes: the paper gives you the contract; the repo gives you the invocation. Neither substitutes for the other, and an agent that reads only one produces confidently wrong runs.

Using paperclip for the paper side

paperclip is the right tool here and I verified it end-to-end on a live paper. The reason it beats "download the PDF and paste it into context" is sub-section addressability: the paper is exposed as a virtual filesystem where individual sub-sections are separately readable files, so the agent fetches Evaluation metrics without paying for the introduction and discussion.

Listing the sections of the benchmark paper I tested returned, among others: Methods.lines, Datasets and preprocessing.lines, Models selection and setup.lines, Evaluation metrics.lines, Absolute Accuracy Metrics.lines, Relative Effect Capture Metrics.lines, Differential Expression Recovery Metrics.lines, Distributional Similarity Metrics.lines, E-distance.lines, TRADE.lines, Data availability.lines, and Code availability.lines. Each metric family is its own addressable read — which is precisely the granularity the harvester wants.

# NOTE: on this machine the paperclip launcher's shebang resolves python3 -> 3.8,
# which its vendored urllib3 cannot import. Pin the interpreter:
PC="/usr/local/bin/python3.10 $HOME/.local/bin/paperclip"

# 1 · locate the benchmark paper; returns a stable ID (bio_ = bioRxiv)
$PC search -s biorxiv "single-cell perturbation response prediction benchmark"

# 2 · discover what is addressable before reading anything
$PC ls /papers/<ID>/sections/

# 3 · pull ONLY the run-critical sections, each as its own budgeted read
$PC cat "/papers/<ID>/sections/Evaluation metrics.lines"
$PC cat "/papers/<ID>/sections/Datasets and preprocessing.lines"
$PC cat "/papers/<ID>/sections/Relative Effect Capture Metrics.lines"

# 4 · the paper -> repo bridge, with citable line numbers
$PC cat "/papers/<ID>/sections/Code availability.lines"
#   L145: ... available via GitHub at: https://github.com/TianGzlab/scPerturbBench

# 5 · targeted retrieval instead of whole-section reads, when you know the term
$PC grep --bool "E-distance AND control" /papers/<ID>/
$PC grep --bool --block-type table --section results "Pearson" /papers/<ID>/

# 6 · fan the same extraction across every model's paper, deterministically
$PC search --config harvest_workflow.yaml
$PC map --from <SEARCH_ID> "extract entrypoint, env constraints, and input layer expectations"

# 7 · persist a generated artifact back into the workspace (the only way that works)
$PC upload modelcards/scgpt.json --into /benchmark-context/

Three practical notes that shape the harvester's design:

  • It is budget-aware by construction. Reads print a token count up front ([~487 tokens total, showing first ~1000 chars]) and truncate by default, with --full, cat > file, and in-file grep as the escape hatches. Build the harvester to grep first and --full only on a hit — the guidance explicitly warns against cat on a whole content.lines.
  • Every extracted field carries a citation. Because reads are line-addressed, a ModelCard field can record bio_…/sections/Code availability.lines:145. Make that mandatory — an uncitable field is a hallucinated field, and this is the cheapest hallucination check available.
  • Use search --config workflow.yaml for the fan-out. A declarative workflow file keeps the harvest reproducible across N models instead of N ad-hoc agent conversations.

Using the Results section — for verification, not for running

The Results section does not tell an agent how to run anything. It is still worth harvesting, for one specific job: a reproduction check. Extract the paper's reported numbers into the same tidy schema the harness emits, and the Evaluate stage gets a free assertion — does our run land near the published value for the models and datasets that overlap? A large gap is the single most informative signal that the adapter is wrong, and it costs one extra extraction.

Keep this strictly advisory. It flags a discrepancy; it never overwrites a computed number, and the harness must not tune toward it.

Repo extraction — what to read, in order

Do not point an agent at a repo and say "figure it out." Read a fixed priority list, cheapest and most-authoritative first, stopping when the ModelCard is complete:

PriorityTargetYields
1config/*.yaml, configs/Declared hyperparameters, task wiring, dataset keys — structured, no inference needed
2requirements.txt, environment.yml, pyproject.toml, DockerfileThe env block, verbatim. Never let an agent paraphrase pins
3Entrypoint (run_*.py, train.py, __main__), --helpCall signature and required flags
4Tutorial notebooks / examples/The real expected input layout — usually more honest than the README
5Data-loading + preprocessing functionsWhich layer must be raw counts vs log-normalized; gene-filtering side effects
6README, then open/closed issuesCheckpoint URLs; known breakages. Issues are where the undocumented gotcha lives

The harness I inspected illustrates why step 1 is first — and also why you should not simply adopt someone else's registry. Its models.yaml entry is only four fields (name, script, metrics_script, tasks): no environment, no hyperparameters, no entrypoint contract. It presumes a human already knows how to run each model. The ModelCard in §7 is deliberately fatter, because the agent has to make that knowledge explicit.

4The gates

An agentic pipeline is only as trustworthy as what it refuses to pass through. Four gates, cheapest first.

1
Contract test — does the adapter satisfy the ABC?
Static: required methods present, correct signatures, declared pred_type, and no import of any metric module (a lint rule, because this is the one boundary that must never blur). Runs in milliseconds on generated code.
Catches: the most common LLM-codegen failure — a plausible module that does not fit the interface.
2
Smoke run — a ~200-cell toy fixture
Every model runs a tiny synthetic dataset end to end. Assert output shape, gene order identical to the frozen reference, dtype, no NaN, and bit-identical output under a fixed seed. Seconds per model.
Catches: shape transposition, silently reordered genes, nondeterminism — before you spend GPU-hours.
3
Baseline sanity — is the model beating trivial?
Mandatory naive baselines run in the same matrix as first-class entries: control-mean, train-perturbation-mean, and an additive baseline. Any model that fails to beat control-mean on Δ-correlation is flagged, not quietly ranked.
Catches: the standard embarrassment in this field — sophisticated models losing to the mean, hidden by metrics computed on absolute expression.
4
Adversarial audit — an agent told to break the result
Prompted to refute, not confirm. Checks: split leakage (does an "unseen" compound have a near-identical scaffold in train?); pretraining contamination (did a foundation model's pretraining corpus include this dataset?); degenerate predictions (constant output, or near-copies of the control profile); metric–pred_type mismatch (a distributional metric scored against a mean-profile prediction).
Catches: the failures that pass every mechanical check and still make the leaderboard wrong.

Contamination deserves emphasis because it is specific to this moment. Single-cell foundation models are pretrained on large public corpora that plausibly include the benchmark's own dataset. There is no library check for this. The auditor's job is to read each model's pretraining-data description via paperclip and cross-reference the accessions in the dataset's provenance — a comprehension task, and a genuinely good use of an agent.

5Chemical perturbation: what changes

Most of this space's tooling was built for genetic perturbation. Small-molecule benchmarking breaks two assumptions.

Perturbation identity is not a label — it is a molecule with a dose. A genetic perturbation is a gene symbol: exact string matching is the right notion of "same perturbation" and "unseen." A compound is not. "Vorinostat", "SAHA", and "MK0683" are the same molecule; a random split on the name string leaks. Requirements:

  • Canonical SMILES as the join key, with the trade name kept only as a display field. Add an InChIKey column so identity survives round-tripping.
  • Murcko scaffold splits (RDKit) for the unseen-compound task, not random splits. Otherwise a close analog of the held-out compound sits in train and the reported generalization is fictional. This is the audit's single highest-value leakage check for chemical data.
  • Dose is a coordinate, not metadata. dose_uM as a numeric column, and unseen dose as a first-class split alongside unseen compound and unseen cell line. A model that ignores dose should be visibly penalized by the split design, not accidentally rewarded.
  • Time point too, where the dataset has one — a 6h and a 24h response to the same compound are different targets.

Controls are per-plate, not global. Chemical screens carry vehicle controls (DMSO) with plate-level batch structure. Since the metrics that matter are computed on Δ-from-control, which control you subtract changes the number. The dataset contract must name the matching control group explicitly per observation, and the harness must never infer it.

6Existing tools: what to reuse, what to build

Reuse aggressively for data structures, metrics, containers, and orchestration. Build only the four things that encode your comparability guarantees.

NeedToolVerdictWhy
Paper context extractionpaperclip Reuse Verified working on a live paper. Sub-section addressability, line-level citations, token counts up front, and a declarative --config workflow for the fan-out. This is the stage's answer.
Data structures & single-cell opsanndata, scanpy Reuse On PyPI, universal in this field. .h5ad is the only sane interchange format here — every model already speaks it.
Perturbation-specific metricspertpy Reuse On PyPI. Provides E-distance and related perturbation statistics — do not reimplement distributional metrics.
Chemistry: scaffolds, canonical SMILESRDKit Reuse On PyPI. Murcko scaffold decomposition and SMILES canonicalization are solved; the chemical splits in §5 depend on it.
Splits & metric reference implementationsperturbench (Altos Labs) Reuse ⚠ source-only Genuinely useful for split logic and metric definitions — but it is not on PyPI (I checked: 404). Vendor it from GitHub at a pinned commit; never write pip install perturbench in a lockfile.
Reference harness & model wrappersscPerturbBench Mine, don't adopt Excellent source of per-model invocation knowledge and task definitions, and the paper→repo bridge works. But run_benchmark.py subprocesses out to a per-model metrics_script and writes no results itself — adopting its runner inherits the comparability bug in §1.
DAG execution, resume, shardingSnakemake (or Nextflow) Reuse Do not write a job runner. You need content-addressed resume, cluster/cloud submission, and per-rule containers — all of it exists. Snakemake if the team is Python-native; Nextflow if you already run nf-core.
Environment isolationDocker / Apptainer Reuse Non-negotiable, not optional. These models have mutually unsatisfiable dependency sets; one shared env is how the matrix silently shrinks to whatever installed last. Apptainer for HPC.
Agent orchestrationClaude Agent SDK / Claude Code subagents Reuse You need tool-use loops, filesystem access, and subagent isolation — all provided. Keep agents as stateless functions over artifacts so a rerun is cheap and inspectable.
Run trackingMLflow / W&B Optional A run manifest plus metrics.parquet already gives full traceability. Add a tracker only if humans need live dashboards during long runs.
Adapter ABC + contract tests— Build This is the interface every generated adapter is checked against. It is the load-bearing artifact and it must be yours, small, and frozen.
Metric registry (single evaluation site)— Build Thin: wraps pertpy/scipy implementations, but declares for each metric its on basis (delta / absolute / distribution) and required pred_type. This declaration is what makes mismatches catchable.
ModelCard + ConflictLedger schema— Build The agent↔code contract. Nothing off the shelf models "this field came from paper line 145, that one from the repo, and they disagree."
Audit checks— Build Scaffold-leakage, pretraining contamination, degeneracy, and baseline sanity are specific to this benchmark's semantics. Small, high-value, and no library will have them.

Net: roughly four modest components to write. Everything heavy — the DAG engine, containers, the single-cell stack, the chemistry, the paper extraction — already exists and is verified available.

7Interfaces the adjacent stages should emit

Out of scope to build, but the runner's quality is capped by these. Each is small.

From the dataset stage — the .h5ad contract

One AnnData file per dataset, splits already materialized as a column, plus a frozen gene order and its hash. If splits are computed at run time, two models can be evaluated on different held-out sets and the comparison is void.

# adata.obs — required columns
perturbation        # canonical SMILES for chemical; gene symbol for genetic
perturbation_name   # human-readable display only; never a join key
inchikey            # chemical only — identity that survives round-tripping
dose_uM             # float; 0.0 for controls
time_h              # float; where the dataset has a time axis
cell_type           # string
is_control          # bool
control_group       # which control THIS cell is compared against (plate/batch-aware)
batch               # plate or run
split               # {train, val, test} — MATERIALIZED, not computed at run time
split_name          # e.g. "scaffold_unseen_compound_seed0"

# adata.layers
counts              # raw integer counts — required; models disagree on what they want
X                   # log1p-normalized; declare the transform in uns

# adata.uns
gene_order_sha256   # hash of var_names, in order — the anti-silent-reorder check
normalization       # e.g. {"target_sum": 1e4, "log1p": true}
dataset_sha256      # content address of the file itself
provenance          # accessions + DOI, so the auditor can check contamination
split_recipe        # how splits were made, incl. scaffold method + seed

From the metrics stage — a declarative spec, not a script

The critical fields are on and requires_pred_type. They let the harness reject a metric–prediction mismatch mechanically instead of producing a meaningless number.

metrics:
  - id: delta_pearson
    family: relative_effect          # absolute | relative_effect | de_recovery | distributional
    on: delta                       # delta | absolute | distribution  <- load-bearing
    requires_pred_type: mean_profile
    aggregate_over: [perturbation, cell_type]
    higher_is_better: true
    gene_set: hvg_2000               # or de_top_50 — must be explicit
  - id: e_distance
    family: distributional
    on: distribution
    requires_pred_type: single_cell   # mean-profile models are N/A here, not zero
    higher_is_better: false
mandatory_baselines: [control_mean, train_perturbation_mean, additive]
bootstrap: {n: 1000, seed: 0}

Note requires_pred_type in action: a model that emits only a mean profile is not applicable to E-distance. Recording that as N/A-with-reason rather than as a bad score is the difference between an honest leaderboard and a misleading one.

The upstream stage supplies the top block; Context Harvest fills the rest, every field cited.

What this stage emits downstream

# predictions — one file per matrix cell
predictions/{model}/{dataset}/{split}/{seed}.h5ad
  obs: perturbation, cell_type, dose_uM, pred_type
  var: gene order identical to dataset gene_order_sha256   # asserted, not assumed

# metrics — tidy long form, one row per (model, dataset, split, seed, metric, group)
metrics.parquet
  model, dataset, split, seed, metric_id, group_key, value, ci_low, ci_high, n, status
  # status ∈ {ok, na_pred_type_mismatch, na_model_failed, flagged_below_baseline}

# run manifest — makes the whole thing reproducible
manifest.json
  spec_sha256, dataset_sha256, gene_order_sha256
  per model: repo commit, image digest, adapter.py sha256, ModelCard sha256
  seeds, hardware, wall time, harness git sha, quarantined models + reason

Two properties do the work here. Tidy long form means adding a metric or a model never changes the schema — the report is a groupby, not a rewrite. status as a first-class column means a missing number always carries its reason, so nothing disappears silently between the runner and the leaderboard.

8Build order

Deliberately inverted from the diagram: build the deterministic spine first, add agents only where the spine is blocked by comprehension.

  1. The ABC and its contract tests. Everything else is defined against this. Freeze it early.
  2. The metric registry and Evaluate, on synthetic predictions. Verify the metrics on data where you know the answer, before any real model exists.
  3. The toy fixture and the smoke gate. A ~200-cell dataset that runs in seconds. This is the highest-leverage artifact in the project — it makes every later iteration cheap.
  4. One model, fully hand-written. No agents. Prove the spine end to end, and learn what a ModelCard actually needs to contain.
  5. The harvest agent — paperclip + repo → ModelCard. Now you know the target schema, because step 4 taught you.
  6. The adapter synthesizer, against gates that already exist and already pass for the hand-written model.
  7. Scale the matrix under Snakemake with containers per model.
  8. The auditor and the report.

Writing the harvest agent before step 4 is the tempting mistake: you would be generating a schema you have not yet validated against a working run, and every downstream gate would be guessing what to check.
