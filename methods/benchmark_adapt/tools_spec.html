methods/benchmark_adapt · tool spec

What each tool in this harness actually does

Written for a computational biologist reading this codebase for the first time. You don't need prior familiarity with agent frameworks to follow it — every agentic-development term is defined inline, at first use, in the amber callouts below.

Companion to README.md (setup + commands) and ../planning/plan_unified.md (the full pipeline this harness is half of).

This folder answers one question: given a paper's model already wrapped in a working Docker image, and a structured description of what that model expects (model_contract.yaml), how do you turn it into a tested, PR-ready benchmark component? Below is the mechanism, then each tool's job in it.

1Core terms used throughout

Agent
A program that loops: read some state, ask a language model what to do next, run that one action, observe the result, repeat — until the task is done or a limit is hit. Distinct from a single one-shot LLM call.
LLM (large language model)
The model being called at each loop step to decide the next action — e.g. GPT- or Claude-family models. It has no memory between calls except what the agent explicitly re-sends.
Non-deterministic
Running the same input twice can produce different output. True of any step that calls an LLM; false of everything else in this harness (see the diagram below).
Container / image
A Docker image is a snapshot of a filesystem plus installed software; a container is one running instance of that snapshot. "Built image" means dependencies are already installed — nothing gets `pip install`-ed at run time.
Sandbox
An isolated execution environment (here, a container) that untrusted or agent-generated code runs inside, so it can't touch the host filesystem or credentials.
Trajectory
The full, ordered log of every command an agent ran and every result it saw during one task — the record that lets a human reconstruct why the agent did what it did.

3The tools

Each card: what it is, any jargon it introduces, and what specifically breaks in this harness if it's missing.

Agent · writes code once

mini-swe-agent

A minimal, bash-only agent (see glossary above): read a file, decide on one shell command, run it, look at the output, repeat. It's what actually writes script.py in harness/synthesize_adapter.py, running inside the handed-off Docker image so it can execute the real model, not just read its source.

Jargon: "bash-only" means the agent's only tool is running shell commands — no separate file-edit/search/browser tools, just bash. That constraint is deliberate: it keeps the trajectory a plain, linear list of commands, which is what makes it auditable.
Missing it: nothing writes the adapter — script.py stays the NotImplementedError stub the templates seed.
Deterministic · the environment

The built Docker image

Not built here — handed off from the other half of the pipeline (RepoLaunch, upstream). This harness only ever points at an image tag; it never constructs one, and the agent never hand-writes install steps.

Jargon: "image tag" is just the name:version string Docker uses to identify a specific built image (e.g. example-chem-perturbridge:a1b2c3d) — not a metadata label, just an address.
Missing it: the agent has nowhere to actually execute the model, so it can only guess at behavior from reading source — exactly the failure mode this harness exists to avoid.
Deterministic · the interface contract

Viash convention (+ viash_shim.py)

Every OP3 method is a config.vsh.yaml + script.py pair following a fixed convention: a par dict carries inputs in, a fixed output path carries predictions out. harness/viash_shim.py runs a raw script this way locally, standing in for the full viash build tool until it's on the machine.

Jargon: a "component," in Viash's vocabulary, is one script plus its config file. par is just a Python dict — Viash's build step injects real values into it in place of the placeholder defaults a script ships with for local testing.
Missing it: every method would need its own bespoke runner, and viash ns test (the eventual real gate) would have nothing to build.
Verification · runs the adapter, never writes it

pytest — "the Gauntlet"

Six checks in gauntlet/, each running the synthesized script.py under a different condition (see the diagram above) and asserting something about the output. No LLM anywhere in this stage, by design — the whole point is a standard the agent can't argue with.

Jargon: pytest is a Python testing framework — a "fixture" is a piece of setup code (here, the frozen dataset and the already-run predictions) that multiple checks reuse instead of each rebuilding it; an "assertion" is a statement that halts the test with a message if it's false.
Missing it: a model that collapsed to predicting the training mean, or emitted the wrong layer entirely, would score "successfully" with zero indication anything was wrong.
Deterministic · the data structure

AnnData + the tiny fixture

fixtures/make_tiny_fixture.py generates a frozen, seeded de_train.h5ad / id_map.csv pair: 500 genes, 2 cell types, 8 compounds, gene order pinned by a recorded SHA256. Small enough that the whole Gauntlet runs in under two seconds.

Jargon: "seeded" means the random-number generator's starting state is fixed, so re-running the generator produces byte-identical output every time — not a statement about the data's biological meaning.
Missing it: every Gauntlet check needs something concrete to run the adapter against; without a frozen fixture, "does the gene order match" isn't answerable.
Deterministic · does the output actually exist

run_component.py

A rendered config.vsh.yaml/script.py that were never executed against real input aren't a finished deliverable, they're an untested claim. harness/run_component.py runs the synthesized script through viash_shim against real data and confirms the declared output file actually landed and is a readable AnnData — shape, layer names, obs/uns keys. Deliberately computes no score; scoring a method's predictions is a separate, later concern from generating them.

Jargon: none new here — reuses the same par/meta injection viash_shim.py already does for the Gauntlet.
Missing it: the only evidence the adapter works is that it compiled — no proof it actually runs, let alone produces a sane output file.
Deterministic · citation discipline

JSON Schema (harness/contract.py)

Validates model_contract.yaml before anything downstream trusts it: every scientific field must either say "unknown" or carry a citation like PAPER_ID:L210-L225 that resolves to a real line. A value with no citation is a validation error, not a warning.

Jargon: a JSON Schema is a machine-checkable description of what shape a data file is allowed to take — here, enforcing that every field is either the literal string "unknown" or a value paired with a citation, nothing else.
Missing it: a wrong-but-confident field (say, the wrong gene count) would corrupt every score downstream with nothing catching it before the adapter gets written.
Not used directly in this folder: Serena and RepoLaunch belong to the other half of the pipeline (repository comprehension + environment build) — they're what produces the Docker image and the contract this harness consumes, not something benchmark_adapt/ calls itself. Modal (cloud GPU) is discussed in the broader plan but isn't wired into anything here — see ../planning/method-integration-todo.html item C5.

4The Gauntlet, check by check

CheckWhat it doesWhat it's actually catching
G1 layer/unit conformance Output layer literally named prediction (never the input layer's own name) must be finite, in range A model emitting the wrong quantity under the right-looking column name — scores silently, with no runtime error
G2 id_map / gene-space alignment obs_names must equal id_map['id'] exactly, in order (not cell_type/sm_name columns); gene identity must match, no reindexing Any reliance on an automatic "fix the alignment for me" fallback, which would hide a real mismatch instead of failing on it
G3 perturbation sensitivity Shuffle sm_name, require the prediction to change A model that collapsed to predicting the per-cell-type training mean, ignoring the compound entirely, while still scoring plausibly
G4 no network at inference Blocks any socket call during prediction, inside the actual subprocess A model quietly re-downloading a copy of evaluation data during inference
G6 output sanity Correct shape, no NaN/Inf Basic execution failures that would otherwise surface only as a downstream crash
G7 stochastic tolerance Re-run, compare — left unresolved on purpose Nothing yet — no tolerance number has been decided by the team. The check skips loudly rather than silently passing on an invented threshold.

See README.md for setup and the exact commands to run all of this yourself, and ../planning/plan_unified.md for how this folder's output feeds into the rest of the pipeline.
